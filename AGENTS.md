# AGENTS.md — okay-kotlin

## For agents writing code with okay-kotlin

okay-kotlin is algebraic effects for Kotlin 2.4 (JVM, JS, native), no dependency: an effect is an interface of suspend
functions, a program's effects are its context parameters, a handler implements the interface and runs the body.

```kotlin
repositories { maven("https://okay-effects.github.io/okay-kotlin/maven") }
dependencies { implementation("io.github.okay-effects:okay-kotlin:0.1.0") }
```

### The model: effect, program, handler, run (from `ReadmeTest`)

```kotlin
import okay.kotlin.*

// an effect: an interface of suspend functions
interface Accounts {
    suspend fun balance(account: String): Int
    suspend fun deposit(account: String, amount: Int)
    suspend fun withdraw(account: String, amount: Int)
}

// a program: its context parameters are everything it may do; the compiler checks it
context(accounts: Accounts, fail: Fail<String>)
suspend fun transfer(from: String, to: String, amount: Int) {
    ensure(accounts.balance(from) >= amount) { "$from has less than $amount" }
    accounts.withdraw(from, amount)
    accounts.deposit(to, amount)
}

// a handler: implements the effect (here on another effect, Store) and runs the body with it
context(store: Store<String, Int>)
suspend fun <A> onStore(body: suspend context(Accounts) () -> A): A = context(object : Accounts {
    override suspend fun balance(account: String) = store.load(account) ?: 0
    override suspend fun deposit(account: String, amount: Int) = store.save(account, balance(account) + amount)
    override suspend fun withdraw(account: String, amount: Int) = store.save(account, balance(account) - amount)
}) { body() }

// run once, at the entry: every effect handled inside
val (db, result) = runEffects {
    inMemory(mapOf("ann" to 100, "bob" to 0)) {          // Store: a map in a test, a database handler in production
        onStore { either<String, _> { transfer("ann", "bob", 70) } }
    }
}
// result: Right(Unit); db: {ann=30, bob=70}
```

- Wrapping a handler is delegation: `context(object : Accounts by accounts { override ... }) { body() }`.
- Control (ending or taking the rest of the body) is `handle { prompt -> ... }` with `prompt.abort(v)` or
  `prompt.shift { k -> ... }` (README "Writing a handler": `either`, `answering`).
  An effect answered in place should be a plain implementation, not a `shift` (~20x slower).
- Standard effects and handlers: `State`/`state`, `Reader`/`reader`, `Writer`/`writer`, `Fail`/`either`,`recover`,
  `Abort`/`optional`, `Emit`/`collect`, `Choose`/`all`,`first`, `Fresh`/`numbered`, `Randomness`/`seeded`,
  `Store`/`inMemory`, `Clock`/`virtualTime`, `Log`/`logged`,`logTo` (README table).
- The other style, effects as data (`okay.kotlin.effects`: `Prog<F, R, A>`, engines `Machine` and `Direct`), is in
  the README section "Effects as data".

### Design rules

- Business logic = suspend functions whose context parameters are effects; the signature says what it may do. A
  function with `context(accounts: Accounts, fail: Fail<String>)` cannot touch anything else through okay.
- Real resources (DB, HTTP clients, files, clock, keys) only inside handlers the host builds at the entry point;
  programs receive effects, data and ids, never a live client.
- Run only at the entry: one `runEffects { ... }` (or `runBlocking { ... }` if the body waits on real I/O). Never call
  `runEffects` inside a program; install handlers inside the program (`either<String, _> { ... }`, `onStore { ... }`).
- Sensitive effects under audit: the handler gives its body a `Vault`, not the capability, and the program gets the
  capability only inside `audit(vault, interceptor) { ... }`. Interceptors: `observer { op, outcome -> ... }`,
  `guard { op -> ... }` (throw `Refused(op, reason)` or `raise`), composed with `+`; any capability can be wrapped by
  `effect.intercepted(interceptor)`. Your own effects get `intercepted` generated by `@Effect` + the KSP plugin
  (`ksp("io.github.okay-effects:okay-kotlin-ksp:0.1.0")`, `id("com.google.devtools.ksp") version "2.3.12"`).

```kotlin
// from InterceptTest: the program can pay only where the auditor sees and may refuse each payment
val limit = guard { op -> if ((op.args[1] as? Int ?: 0) > 1000) throw Refused(op, "over the limit") }
val auditor = observer { op, outcome -> trail += "$op: ${outcome.getOrNull()}" }
runEffects { payments { vault -> audit(vault, auditor + limit) { salaries() } } }
```

- Tests swap handlers: `inMemory` for the database store, `virtualTime` for the clock, `seeded(seed)` for randomness,
  your own in-memory implementation of your interface — no mocking frameworks.
- No ambient effects in business code (`System.currentTimeMillis`, `Random`, I/O, env, threads, globals): use or
  declare an effect (`Clock`, `Randomness`, `Fresh`, `Log`, your interface).
- Multi-shot is real, never by replay: `k.copy()` copies the rest's frames (JVM and JS only; native has none).
  `Choose` with `all { ... }` / `first { ... }` enumerates/backtracks. On every platform, the data style's `Machine`
  engine has `k` as data, multi-shot natively.

### Pitfalls

- Type parameters of a handler are not inferred from what the body asks of its context: write
  `either<String, _> { ... }`, `collect<Int, _> { ... }`.
- `runEffects` throws "the program waits for something outside its handlers" if the body suspends on a timer/thread;
  run it in `runBlocking { ... }` (handlers are ordinary suspend functions and work under kotlinx.coroutines).
- Multi-shot is refused across a delimiting handler: `all { either { ... } }` fails, `either { all { ... } }` works.
  Heap objects reachable from frames are shared by copies; keep per-branch state in locals.
- JVM multi-shot over a `for` on a JDK collection needs `--add-opens java.base/java.util=ALL-UNNAMED`; from JDK 26
  also `--enable-final-field-mutation=ALL-UNNAMED`. Ranges and `repeat` need nothing.
- Handlers are lexical (capabilities): a function made under one handler asks that handler even if called under
  another of the same effect. A capability kept after its handler returned fails if that handler takes the rest.
- A general (shifting) handler takes one operation at a time: children shifting to the same prompt concurrently are
  not supported.

## For agents working on this repository

Read before anything else, then `docs/design.md`.

- Kotlin 2.4 (context parameters, stable), multiplatform: JVM always, JS and native when asked. Package `okay.kotlin`,
  artifact `okay-kotlin`. The core has NO dependency: the continuations are the standard library's
  (`kotlin.coroutines.intrinsics`); kotlinx.coroutines is a test dependency of the JVM, for the interop tests only.
- IDIOMATIC KOTLIN FIRST: an effect is an interface of suspend functions; a program's effects are its context
  parameters; a handler is a function that implements the interface and runs the body with it (`context(impl) {
  body() }`); wrapping a handler is delegation (`object : Store<K, V> by store`). No effect is data, no operation a
  class, unless an interface cannot say it.
- An effect answered in place is a plain implementation — a virtual call. Only control takes the rest of the body:
  `handle` and `Prompt.shift` / `abort`. Do not make an answered-in-place effect shift: it is ~20× slower.
- Interception is a wrapper of a capability: `intercepted(interceptor)`, each suspend function an `Operation` through
  `Interceptor.around`. The standard effects' wrappers are hand-written in `Intercepted.kt` and must look exactly like
  what `ksp/` generates for `@Effect`; a new standard effect gets its wrapper and a line in `InterceptTest`.
- THE SPEC is Forster, Kammar, Lindley, Pretnar, ICFP 2017 (EFF, MON, DEL); `SpecTest` its examples and rules,
  `docs/design.md#against-the-literature` the comparison. Deliberate differences: handlers chosen lexically
  (capabilities), not dynamically; multi-shot only where a frame can be copied (JVM, JS). `k` is a value: never
  assume it is resumed inside its clause.
- Multi-shot by COPYING the rest's frames (`Resume.copy`, `Frames.jvm.kt`, `Frames.js.kt`), never by replay (the
  user's rule). Native has none. A copy is taken before `k` is resumed; a delimiting handler between refuses it.
- `okay.kotlin.effects`: effects as data, ONE PROGRAM, TWO ENGINES — `Effects<F>` the interface, `Machine` (CEK,
  okay-scala's) and `Direct` (this library's continuations). Programs and standard handlers are written once, generic
  in `F`; `EffectsTck` holds both engines to the same answers — a new handler or word gets a line there. Rows `With`,
  typed places; a handler gives its body its place, `lift` carries outer ones in.
- No casts, no `!!` in the library. Warnings are errors.
- A handler's type parameters cannot be inferred from what its body asks of the context: tests and docs write
  `either<String, _> { ... }`. Do not "fix" it with overloads that guess.
- Lines at most 120 wide. Commits: plain messages, no attribution trailers.
- `./gradlew check` (JVM: core, the generator on `examples`); `./gradlew -Pplatforms=jvm,js,native :core:allTests`;
  `./gradlew :bench:jmh`. The README's example is `ReadmeTest`: change both together.
